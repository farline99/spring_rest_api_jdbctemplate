# Лабораторная работа № 5 - REST API JDBCTemplate

## Цель работы

Разработать REST API на Spring Boot для хранения владельцев телефонов, их адресов и номеров. Реализовать создание, чтение, полное и частичное обновление, удаление записей, замену и обмен номеров, а также расчёт статистики.

## Архитектура проекта

- **Стек:** Java 21, Spring Boot 3.5.7, Maven, Spring Web, Spring JDBC, Bean Validation, H2.
- **СУБД:** H2 в памяти (`jdbc:h2:mem:phoneowners;DB_CLOSE_DELAY=-1`). PostgreSQL в проекте не используется. Таблицы создаются скриптом `schema.sql` при запуске приложения и удаляются вместе с базой после его остановки. Начальные данные отсутствуют.
- **Основные слои:**
  - `PhoneOwnerController` принимает HTTP-запросы, передаёт данные сервису и возвращает DTO ответа;
  - `PhoneOwnerService` реализует бизнес-логику, проверяет входные данные и уникальность номера, управляет транзакциями и рассчитывает статистику;
  - `PhoneOwnerRepository` работает с H2 через `JdbcTemplate`: выполняет выборки, вставку, обновление и удаление записей;
  - `PhoneOwnerRowMapper` преобразует строку объединённой выборки владельца и адреса в объект `PhoneOwner`;
  - пакет `entity` содержит модели `PhoneOwner` и `Address`;
  - пакет `dto` содержит модели запросов, ответов, частичного обновления и статистики;
  - `ApiExceptionHandler` преобразует исключения в единый JSON-формат ошибки.
- **Ключевые аннотации:** `@SpringBootApplication` запускает приложение; `@RestController`, `@RequestMapping`, `@GetMapping`, `@PostMapping`, `@PutMapping`, `@PatchMapping`, `@DeleteMapping`, `@PathVariable` и `@ResponseStatus` описывают REST-маршруты и коды ответов; `@RequestBody`, `@RequestParam` и `@Valid` связывают и проверяют входные данные; `@Repository`, `@Service` и `@Transactional` формируют слои приложения; `@RestControllerAdvice` и `@ExceptionHandler` обрабатывают ошибки; `@NotBlank`, `@NotNull`, `@Size` и `@Pattern` задают правила валидации.
- **Описание моделей данных и DTO:**
  - `PhoneOwner` содержит `id`, `lastName`, `firstName`, `middleName`, `phoneNumber` и связанный объект `Address`.
  - `Address` содержит `id`, `postalCode`, `country`, `region`, `district`, `city`, `street`, `house` и `apartment`. В таблице `addresses` поле `owner_id` уникально и связано внешним ключом с `phone_owners`.
  - `PhoneOwnerRequest` и `AddressRequest` описывают обязательные данные для создания и полного обновления записи.
  - `PhoneOwnerPatchRequest` и `AddressPatchRequest` содержат необязательные поля для частичного обновления. Если поле не передано или равно `null`, используется текущее значение.
  - `PhoneNumberUpdateRequest` содержит новый номер одного владельца, а `PhoneNumberReassignmentRequest` содержит номер владельца-источника и `targetOwnerId` второго владельца.
  - `PhoneOwnerResponse`, `AddressResponse` и `PhoneNumberReassignmentResponse` формируют ответы API без служебных ссылок между сущностями.
  - `PhoneOwnerStatistics` содержит общее количество владельцев, число стран и городов, самый частый город, самую частую улицу и распределение записей по странам и городам.
  - `ApiError` содержит `timestamp`, `status`, `error`, `message` и `fieldErrors`.
- **Описание реализованных мапперов:**
  - `PhoneOwnerRowMapper` реализует `RowMapper<PhoneOwner>`. Он читает результат SQL-запроса с объединением таблиц `phone_owners` и `addresses`, создаёт объекты `Address` и `PhoneOwner` и заполняет их полями с учётом псевдонимов `owner_id` и `address_id`.
  - Отдельных классов MapStruct или ModelMapper в проекте нет. Преобразование сущностей в ответы выполняет метод `toResponse` сервиса, который собирает `AddressResponse` и `PhoneOwnerResponse`.
  - Методы `applyOwner` и `applyAddress` переносят данные из входных DTO в сущности и удаляют лишние пробелы по краям строковых значений.
  - При частичном обновлении сервис объединяет переданные поля с текущими значениями через `valueOrExisting`, после чего повторно валидирует полный запрос.

## Алгоритм работы

1. Приложение запускается командой `mvn spring-boot:run` и принимает запросы по адресу `http://localhost:8080/api/owners`. Корневой адрес `/` не является страницей приложения: проект не содержит HTML-интерфейса, поэтому обращение к корню возвращает ошибку `404`. Проверка методов выполняется через `curl` или Postman.
2. `POST /api/owners` проверяет обязательные поля, формат телефона и его уникальность. При успешной проверке владелец и адрес сохраняются в двух таблицах, после чего возвращается созданная запись со статусом `201 Created`.
3. `GET /api/owners` возвращает список всех владельцев, а `GET /api/owners/{id}` возвращает одну запись вместе с адресом. Для отсутствующего идентификатора возвращается `404 Not Found`.
4. `PUT /api/owners/{id}` полностью заменяет данные владельца и адреса. Перед сохранением выполняется валидация и проверка уникальности номера среди других записей.
5. `PATCH /api/owners/{id}` изменяет только переданные поля. Неуказанные значения владельца и адреса остаются прежними.
6. `PUT /api/owners/{id}/phone-number` заменяет номер одного владельца после проверки его уникальности.
7. `PUT /api/owners/reassign` находит владельца по текущему номеру и обменивает его номер с указанным `targetOwnerId`. Для обхода ограничения уникальности номер источника временно заменяется значением `TMP-<UUID>`, после чего обоим владельцам записываются нужные номера.
8. `GET /api/owners/statistics` рассчитывает показатели по всем записям. Query-параметры `country` и `city` необязательны и ограничивают выборку совпадением страны и города без учёта регистра.
9. `DELETE /api/owners/{id}` удаляет адрес и владельца. Успешный ответ не содержит тела и имеет статус `204 No Content`.
10. Ошибки валидации возвращаются как `400 Bad Request` с картой `fieldErrors`. Нарушение уникальности номера возвращает `409 Conflict`, отсутствующая запись возвращает `404 Not Found`, а синтаксически неверный JSON возвращает `400 Bad Request` с сообщением `Некорректный JSON`.

**Маршруты API:**

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| `GET` | `/api/owners` | Список владельцев |
| `GET` | `/api/owners/{id}` | Владелец по идентификатору |
| `GET` | `/api/owners/statistics` | Статистика по всем записям или с фильтрами `country` и `city` |
| `POST` | `/api/owners` | Создание владельца |
| `PUT` | `/api/owners/{id}` | Полное обновление |
| `PATCH` | `/api/owners/{id}` | Частичное обновление |
| `PUT` | `/api/owners/{id}/phone-number` | Замена номера телефона |
| `PUT` | `/api/owners/reassign` | Обмен номеров двух владельцев |
| `DELETE` | `/api/owners/{id}` | Удаление владельца и адреса |

**Правила валидации:** фамилия, имя и отчество обязательны, длина каждого значения не превышает 100 символов. Почтовый индекс обязателен, его длина не превышает 20 символов. Страна, область, район и город обязательны и ограничены 100 символами, улица обязательна и ограничена 150 символами, дом и квартира обязательны и ограничены 30 символами. Номер телефона должен содержать от 7 до 30 символов из набора `+`, цифры, круглые скобки, дефисы и пробелы.

### 1. Создание владельца

`POST /api/owners` сохраняет владельца вместе с адресом и номером телефона и возвращает `201 Created`.

### 2. Список владельцев

`GET /api/owners` возвращает все сохранённые записи. Перед этим запросом через тот же метод были созданы ещё три владельца.

![Список владельцев](screenshots/2.png)

### 3. Получение владельца по идентификатору

`GET /api/owners/1` возвращает одну запись и её адрес.

![Владелец по идентификатору](screenshots/3.png)

### 4. Полное обновление

`PUT /api/owners/2` заменяет данные владельца и адреса и возвращает обновлённую запись.

![Полное обновление](screenshots/4.png)

### 5. Частичное обновление

`PATCH /api/owners/3` изменяет только улицу и дом, сохраняя остальные поля адреса и данные владельца.

![Частичное обновление](screenshots/5.png)

### 6. Замена номера телефона

`PUT /api/owners/3/phone-number` заменяет номер выбранного владельца. В ответе подтверждается новый номер.

![Замена номера телефона](screenshots/6.png)

### 7. Обмен номеров телефонов

`PUT /api/owners/reassign` обменивает номера двух владельцев. В ответе показаны оба владельца с новыми номерами.

![Обмен номеров телефонов](screenshots/7.png)

### 8. Статистика

`GET /api/owners/statistics` возвращает общее количество владельцев, стран и городов, самый частый город, самую частую улицу и распределение записей.

![Статистика владельцев](screenshots/8.png)

### 9. Статистика с фильтрами

`GET /api/owners/statistics?country=Россия&city=Москва` рассчитывает показатели только по записям, которые удовлетворяют обоим фильтрам.

![Статистика с фильтрами](screenshots/9.png)

### 10. Ошибка валидации

`POST /api/owners` с пустыми обязательными полями и некорректным телефоном возвращает `400 Bad Request` и перечень ошибок по полям.

![Ошибка валидации](screenshots/10.png)

### 11. Конфликт номера телефона

Повторное создание владельца с уже занятым номером возвращает `409 Conflict`.

![Конфликт номера телефона](screenshots/11.png)

### 12. Запись не найдена

`GET /api/owners/99` возвращает `404 Not Found` с сообщением об отсутствующем владельце.

![Владелец не найден](screenshots/12.png)

### 13. Удаление владельца

`DELETE /api/owners/3` удаляет владельца и связанный адрес и возвращает `204 No Content`. Последующий запрос списка показывает, что запись с идентификатором `3` отсутствует.
